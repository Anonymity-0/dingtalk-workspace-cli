Beyond parity

八个差异化业务闭环

它们不是“多注册几个名字”，而是将原子调用组织为有状态、有补偿、有界等待和可恢复失败的业务过程。

+record-wrap-up

stop 一次后有界等待所选产物；产物未就绪时保留 taskUuid，绝不把空值当完成。

+upload-and-analyze

本地直传、complete、等待逐字稿/摘要，并可接脑图和发言人洞察；支持 resume 不重复上传。

+mindmap

创建异步任务并按明确的 0/1/2 状态轮询；超时不重复创建。

+speaker-insights

创建发言人总结并轮询；未就绪以非零返回真实 taskId 恢复句柄。

+prepare-asr

会前读取个人热词、计算 add/delete 差异；默认只增，显式 sync 才删除并读回。

+export-pack

将多个产物写入受控目录并生成 manifest；不记录签名 URL、令牌或凭证。

+share

面向多听记、多成员的语义化权限授予，逐项 acknowledgement 与部分写 ledger。

+unshare

权限移除同样默认首错停止；显式 continue 后任一失败仍非零。

Truthful execution

把“空数组成功”从正确性标准中彻底移除

合法业务空集合当然可以成功，但必须先证明响应结构与分页语义正确；内部报错、缺字段和产物未就绪不能被空值吞掉。

读取链路的四层证据

1
响应形状只接受已声明的对象/数组字段；结构漂移直接失败，不降级为空。
2
分页完整性消费 nextToken，检测停滞、成环和“有下一页但无 token”。
3
产物合同summary / transcript 等待必须满足非空与可用条件，不能仅凭 HTTP 成功。
4
稳定投影输出 count、complete、ledger 和恢复信息，避免把原始响应噪声交给 Agent 猜。
成功 = 业务结果有效且完整；“没有报错”或“返回了 []”都不是充分条件。

Review prompts

建议业务评审重点确认

若以下边界成立，本方案可以作为一次性完整交付；未来新增后端原子能力时，再按真实模型补齐，而不是在 CLI 先造概念。

01

是否接受 5 / 4 / 1 对齐结论？

5 项对齐/增强、4 项部分、1 项不可对齐；不以同名率替代平台语义。

02

只读 action-items 是否足够明确？

命令不会写 Minutes Todo，也不会借普通 Todo 对象模拟。

03

写操作确认范围是否合适？

17 个写入口全部 user_required；13 个复杂写入口额外提供契约化 dry-run。

04

是否认可非零 partial failure？

多步流程部分完成时保留 ledger 和恢复句柄，不用零退出掩盖未完成阶段。

05

DWS 差异化闭环是否可作为主路径？

建议优先推广 upload-and-analyze、record-wrap-up、export-pack 与 share/unshare。

06

平台缺口的解锁顺序？

建议优先 Minutes Todo 写 API、Chapter、speaker identity 模型与会议关联索引。
